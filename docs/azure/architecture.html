How a client's Aspen system runs on Azure

One Ubuntu VM runs Aspen behind nginx. Data lives in a private Azure Postgres server; attachments and long-term backups live in a storage account; email goes out through Azure Communication Services; Azure Monitor watches all of it and emails SSS. Names below are Valhalla's, the first client (valhalla.spokanesoftware.com, resource group rg-aspen-valhalla-prod, West US 3).

Backups and recovery

LayerWhat it covers
Postgres automaticRestore the whole database to any minute in the last 35 days. Copies are kept in a second region.
Monthly exportOn the 1st at 10:00 UTC the VM runs pg_dump and uploads it to db-backups. Kept 7 years, protected from deletion.
Backup checkDaily at 12:00 UTC the VM reports the newest export's age to Azure. Older than 33 days raises the backup-overdue alert.
AttachmentsGeo-redundant storage, plus 30-day soft delete on the share.
VM itselfNot backed up on purpose. It holds no data and is rebuilt from the install runbook and a release.
Bad releaseThe last 3 releases stay on the VM. Rollback is pointing current back and restarting.

Known gap: Azure refused to restore into a new Burstable server in West US 3. In an emergency, restore on General Purpose with the CLI command in the install runbook (phase 21) and scale down later.

How an update reaches the VM

  1. Check every repo is clean and pushed, then review what changed: new indexes, seed data, upgrade services, scheduled jobs.
  2. Run the test suites (H2 and Postgres) and record the results.
  3. Build the release on a Mac. It gets a dated folder name and a RELEASE.txt listing every repo's commit.
  4. Copy it to /opt/aspen/releases/ on the VM while the old one keeps running.
  5. Off hours: point current at the new release and restart. About 90 seconds down.
  6. Do any one-time steps, verify the site and logs, write it in the client's install log.

Every command is in UPDATE.md.
